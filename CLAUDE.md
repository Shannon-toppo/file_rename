# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

This folder holds **consumer scripts for the `mv2title` library** (which lives in the sibling `../mv2title/` package and is its own git repo — this folder is *not* part of that repo). The scripts take real audio files, infer a clean song title with `mv2title`, and write it into the file's metadata.

- **`core.py`** — GUI-agnostic shared core (never prints): loads the connection `.env` (`find_env_file()`; dev = `../mv2title/.env`), defines `Track`/`Status`, and implements `download_tracks` (yt-dlp, progress callback + **`on_stage` post-download stage callback** + cancel `threading.Event`), `fetch_metadata` (metadata only, **no download** — flat playlist extraction, returns `filepath=None` QUEUED rows), `infer_titles` (batched, protects `manual=True` **and `skip_infer=True`** rows unless `force=True`), `write_tags` (skip policy lives here), `write_title`, `read_tags` / `track_from_file` (既存タグの読み込み — see Pipeline specifics), `describe_result`, `is_youtube_music` / `use_metadata_title` / `_fetch_ytmusic_title` (the YouTube Music short-circuit — see Pipeline specifics), `read_url_list` (txt URL-list parsing — blank/`#` lines ignored — shared by `download.py -a` and the GUI).
- **`rename.py`** — thin CLI: scans `files/` for audio, then `core.infer_titles` + `core.write_tags`.
- **`download.py`** — thin CLI: `core.download_tracks` per URL (channel name rides along as an artist hint), then infer + write via core.
- **`gui/`** — PySide6 GUI (table-based) on top of `core.py`. See the GUI section below.
- **`files/`** — working directory for audio files (`.mp3`, `.wav`, `.m4a`, `.opus`).
- **`run_gui.py` / `selftest.py` / `file_rename_gui.spec` / `build.ps1` / `build.sh` / `.env.example` / `README_dist.md`** — PyInstaller packaging (`selftest.py` = the `--selftest` diagnostic). See the Packaging section below.
- **`ytdlp_runtime.py`** — fetches / updates / loads yt-dlp **and its EJS companion (`yt-dlp-ejs`)** at **runtime**; neither is bundled in the frozen build. See the Packaging section.

## How it wires to mv2title

Dependencies are declared in this folder's own `pyproject.toml` (uv-managed, `package = false`): **mutagen**, **yt-dlp**, **python-dotenv**, and **mv2title as an editable path dependency** (`[tool.uv.sources] mv2title = { path = "../mv2title", editable = true }`). Run `uv sync` here to create the venv — no `sys.path` manipulation anywhere.

- `core.py` loads `.env` at import via `find_env_file()` — search order ① `app_dir()/.env` (frozen: next to the exe / `.app`) → ② `../mv2title/.env` (dev fallback) — so `BASE_URL`/`API_KEY`/`MODEL`/`SYSTEM_PROMPT` (`ENV_KEYS`) are on `os.environ` before `Config.from_env()` reads them. `app_dir()` is frozen-aware (`sys.frozen`; on mac it resolves out of the `.app` bundle to its parent dir) and `FILES_DIR = app_dir()/"files"`. `apply_env_overrides()` layers GUI-settings overrides on top (priority: override > process env — `_PROCESS_ENV` snapshot taken before load_dotenv > `.env`; an empty override restores the default, keys absent everywhere are removed). `_augment_path_darwin()` (import-time) appends `_DARWIN_EXTRA_PATHS` — `/opt/homebrew/bin`, `/usr/local/bin`, and `~/.deno/bin` (expanded; deno's official-installer location) — to PATH on macOS because Finder-launched apps don't inherit the shell PATH (ffmpeg / deno detection); non-existent entries are appended anyway rather than probed, so the behaviour doesn't vary per machine (tests would too). Don't duplicate env setup in new scripts; import `core` instead.
- Inference uses the mv2title **0.4.0** API: `client = LLMClient(Config.from_env())` (wrapped in `core.make_client()`) and `extract_titles(inputs, client, batch_size=5, bypass_check=True)` with `TitleInput(stem, channel=...)` items; results are `TitleResult` objects (`.title` / `.valid`). 0.4.0 decoupled `bypass_check` from `retry_invalid`, so **a `bypass_check=True` call now retries missing/invalid items too** (see the next section) — the call can cost more than one round-trip; `retry_invalid=0` is the opt-out. The dependency is an unpinned editable path dep, deliberately: older mv2title still runs (degraded, see the same bullet).
- `core.download_tracks` extracts `entry["channel"]` (falling back to `entry["uploader"]`) from yt-dlp into `Track.channel`, so the LLM prompt gets a `[チャンネル名]` artist hint.

## Pipeline specifics

- `bypass_check=True` means results are returned even if validation fails (no in-library retry/raise), so core **guards itself**: `infer_titles` raises `CoreError` (marking all targets `ERROR`) on `len(results) != len(targets)` to avoid mis-assigning titles (results are returned in input order, matched positionally). `write_tags` skips `valid=False` and empty-title rows — except `manual=True` rows, which are written on the user's authority. A row whose title is skipped still gets its `artist`/`album` written when either is non-empty (it stays `PENDING`, with the reason in `error`), so an album/artist edit on an imported file isn't thrown away just because the title is undecided; `write_title` writes each of the three fields only when non-empty, so `title=""` updates the other two.
- **The count guard is not enough: a short LLM response comes back padded, not short.** `check_results` returns one `TitleResult` per *input*, filling any input with no matching output as `title=""` / `valid=False` — so `len(results) == len(targets)` holds and the row just goes blank. Measured (LM Studio + gemma-4-e2b): with the structured-output request (`response_format` = mv2title's strict `json_schema`) the model emits **only the first array element and stops** — `finish_reason=stop`, 37 completion tokens, **`reasoning_tokens=0`** — for any input count, so every run with ≥2 rows lost all titles but the first (the symptom that looked like "inference was skipped for one of two URLs"). The same prompt with no `response_format` returned every item (555 reasoning tokens). **The "constrained decoding leaves no room to think" reading of that was wrong** — `reasoning_tokens=0` is a symptom, not the cause. The real cause was a mismatch between mv2title's prompt and its own schema: `make_json_prompt` asked for a bare *JSON array* while `RESPONSE_SCHEMA` (strict mode → top level must be an object) forces `{"results": [...]}`, so the model started an array, had `{"results": [` imposed by the grammar, and closed after one element. Isolated by bisection: `minItems`/`maxItems`, `strict: false`, a top-level-array schema and an explicit "return exactly N elements" instruction all still gave 1/3, while rewording the prompt to describe the `results` object gave 3/3 twice over — **fixed in mv2title 0.4.1**, which keeps schema-on runs at one call. Two mitigations remain from before that: **mv2title 0.4.0** (Shannon-toppo/mv2title#9) — the partial retry runs under `bypass_check=True`, re-asks the missing items with `use_schema=False`, and latches the whole run to plain prompts once a truncated batch is seen (measured: 12 titles / `batch_size=5` = 4 calls, not 6). `core._retry_missing_titles` did the same thing consumer-side and is **kept commented out** — under 0.4.0 it is not merely redundant but a wasted round-trip on failure (it would re-send exactly what mv2title just sent: schema off, temperature 0.0). It stays as a note for mv2title ≤ 0.3.0 and for the next model that truncates; the measured numbers above live in that comment block. What is *not* redundant and stays live: a row that still comes back empty keeps `PENDING` (so 手入力 / 再推定 / artist-album-only writing all keep working) and carries `EMPTY_TITLE_ERROR` in `error`, and the GUI shows `error` in the 推定タイトル column for **any** row with an empty title (not just `ERROR` rows), so a blank cell is never mistaken for "the row was skipped". **The escape hatch is `core.USE_SCHEMA` (default `True`)**: `infer_titles(use_schema=...)` passes straight through to `extract_titles`, exposed as 設定 の「構造化出力 (JSON スキーマ) を使う」 (`options/use_schema`) and CLI `--no-structured-output`. mv2title's fallback already recovers the titles, so this is purely about round-trips — with a truncating model every run wastes its first batch on a 1-item answer and pays a partial retry, and turning the schema off removes both. Since 0.4.1 fixed the actual cause it is no longer needed for gemma-4-e2b — keep it ON, and treat the toggle as the escape hatch for the *next* model that truncates. Note the plain (`use_schema=False`) path is not perfectly repeatable on LM Studio: measured 4/5 runs at one call, the fifth losing one item to `is_title_match` and paying a retry — same prompt, same input, `temperature=0`, and it alternates with call order, so it is server-side nondeterminism (prompt-cache reuse), not a property of the prompt.

- **YouTube Music URLs skip inference entirely** (`ytmusic_direct=True`, the default on `download_tracks` / `fetch_metadata`, GUI 設定 checkbox `options/ytmusic_direct`, CLI `--no-ytmusic-direct` to turn off). Three parts, each measured against live YTM data:
  - **Detection** — `is_youtube_music(*urls)` is variadic and matches on **hostname** (`music.youtube.com`), tolerating a schemeless paste (`urlsplit` reads `music.youtube.com/...` as a path, so `_hostname()` retries with `//`). It is fed every URL the extraction leaves behind, because yt-dlp **redirects YTM to www.youtube.com** (`WARNING: YouTube Music is not directly supported`) and rewrites each entry's `webpage_url`: the URL passed by the caller, the playlist-level `original_url` / `webpage_url` (both survive as `music.youtube.com`), and the entry's `original_url` (also survives). Never `webpage_url` alone.
  - **The song name is NOT in yt-dlp's metadata.** `entry["track"]` only exists for videos with a 「この動画の音楽」 section — measured `None` on ordinary YTM songs *and* art tracks. So `_fetch_ytmusic_song()` asks YouTube Music itself: POST to `music.youtube.com/youtubei/v1/next` as client `WEB_REMIX`, then `_find_ytmusic_song()` pulls `playlistPanelVideoRenderer.title` for the matching `videoId` (structure is searched recursively, never keyed by position). This is the whole point of the feature: video title `MIMI『 Pale 』feat. 初音ミク` → song name `Pale`; `MIMI『ルルージュ』feat.初音ミク` → `ルルージュ`. ~0.25 s per track. Fallback chain on any failure: `entry["track"]` → video title. The same renderer carries the **artist**: `_byline_artist()` takes the `longBylineText` runs whose `browseEndpointContextMusicConfig.pageType` is `MUSIC_PAGE_TYPE_ARTIST` (joined with `, ` when there are several) — selecting by link target, not by splitting the byline text, because its shape varies (`MIMI • Pale • 2020年` for an album track, `MIMI • 393万回視聴 • 高評価 6.5万 件` for an MV). `use_metadata_title(track, title, artist=...)` fills アーティスト but **never overwrites a non-empty one**, so manual edits and [チャンネル名→アーティスト] survive. `fetch_metadata` runs the same lookup so [情報取得] shows the final song name (linear cost on big playlists — that stage is otherwise flat/cheap).
  - **Plumbing** — `use_metadata_title()` writes `guessed_title` with `skip_infer=True` / `valid=True` / `PENDING`, leaving `stem` alone so the original video title stays visible in 元タイトル (and remains the LLM input if the row is later cleared). `skip_infer` is protected from re-inference exactly like `manual` (cleared by `force=True` or the model's `clear_title`), but is **not** `manual`, so no `✎` prefix. In the GUI worker, a row expanded by [情報取得] carries its `skip_infer` + title onto the real `Track` in `_download_one` — for a 1→N expansion each new row falls back to its own title — and the LLM-unreachable **degraded path still writes those rows** when auto-write is on, since they never needed the LLM.
- **停止（キャンセル）を yt-dlp に伝えるには `DownloadCancelled` を投げるしかない。** 進捗フックから素の `CancelledError` を投げても、`ignoreerrors=True` の `_handle_extraction_exceptions` が「予期しない例外」として `report_error` で握り潰し、**再生リストの次のエントリへ進んでしまう**（実測: 3 件の検索結果に対し停止済みでも 1 件目→2 件目→3 件目と着手し続け、ライブ配信に当たると 280 秒経っても止まらなかった）。`_load_cancel_exception()` が `CancelledError` と yt-dlp の `DownloadCancelled` を多重継承したクラスを作り、`_cancelled(msg)` がそれを返す — `DownloadCancelled` だけは握り潰さず再送出される唯一の例外なので、その場でリスト全体が止まる（呼び出し元は従来どおり `CancelledError` で捕捉できる）。さらに `match_filter` にも同じ判定を置く: 進捗フックはバイトが届き始めてからしか鳴らず、ライブや HLS では最初の 1 個目まで数十秒かかるため、エントリ処理に入る前に止める（`match_filter` から `DownloadCancelled` を投げてよいことは yt-dlp のオプション説明に明記されている）。ただし yt-dlp は `match_filter` 経由の中断で `break_err()` を**引数なしで作り直す**ため文言が英語の既定値に化ける — `download_tracks` が `extract_info` の周りで捕まえて日本語の文言に戻す。
- **yt-dlp の失敗理由は `CoreError` の文言に載る。** `ignoreerrors=True` のため `extract_info` は例外を投げず `None`（または欠けた `entries`）を返すだけで、理由は yt-dlp の `report_error` にしか出ない — ロガーを渡した GUI ではログパネルに流れるが、行の状態欄に出るのは `CoreError` の文言なので、URL は正しいのに「URL を確認してください」と表示されて誤診を招いていた（実例: YouTube が Premium 限定に指定した動画 → `この動画を視聴できるのは、Music Premium のメンバーのみです`）。`_record_ydl_errors(ydl)` が **インスタンスの `report_error` を差し替えて**文言を溜め、`_ydl_error_message(errors, fallback)` が改行を潰し重複を除いて 1 行にまとめる。`opts["logger"]` を常設する手は使えない — yt-dlp は logger があると `to_screen` を `logger.debug` へ流すので CLI の進捗バーが壊れる。`report_error` を持たない実装（テストの代役）では差し替えを諦めて従来の汎用文言（`GENERIC_EXTRACT_ERROR`）に落ちる。
- `write_title` is format-specific: `TIT2` frame for `.mp3`/`.wav` (mutagen ID3), `\xa9nam` atom for `.m4a` (MP4), Vorbis-comment `title` for `.opus` (mutagen `OggOpus`); other extensions raise `ValueError`. Artist and album ride along on the same call — `TPE1`/`TALB`, `\xa9ART`/`\xa9alb`, `artist`/`album` — each written only when non-empty, so an empty field leaves the file's existing value alone. `SUPPORTED_EXTS` / `download.py`'s `--format` choices are limited to these four.
- **Local files are imported with their existing tags.** `read_tags(filepath)` reads 曲名 / 作者 / アルバム名 (the three fields `write_title` writes, via `_ID3_TAG_KEYS` / `_MP4_TAG_KEYS`) and is deliberately **best-effort: it never raises** — no tags, a broken file, an unsupported extension all come back as a dict of empty strings, so one bad file in a folder can't abort the whole import. `track_from_file(path, read_metadata=True)` seeds `guessed_title`/`artist`/`album` from it; a file that **already has a title tag** becomes `skip_infer=True` / `valid=True` / `PENDING` (the same shape as the YouTube Music short-circuit) so the title visible right after 取り込み isn't silently replaced by the LLM on the next 実行 — 「選択行を再推定」 (force) or clearing the row puts it back in the inference path. Files without a title tag stay `QUEUED` with an empty title, exactly as before.
- `download_tracks` can pass audio filters to ffmpeg via `postprocessor_args` (`-af`): **loudness normalization** (`normalize=True` default; target `I` comes from the `loudness` arg, default `NORMALIZE_TARGET_I` = -14 LUFS, TP/LRA fixed — see `loudnorm_filter()`) and **experimental trailing-silence removal** (`trim_silence=True`, default OFF; `TRIM_SILENCE_FILTER` = areverse→silenceremove→areverse, conservative: only ≤ -50dB counts as silence and 1 s is kept so fade-outs survive). Silence trim runs **before** loudnorm so loudness is measured on the trimmed body. CLI flags: `--no-normalize` / `--loudness` / `--trim-silence`.

- **Bitrate and sample rate of the converted file** are decided by `core`'s own extract-audio postprocessor, not by yt-dlp's defaults. `download_tracks(audio_bitrate=...)` takes `None` (ffmpeg's default — 64 kbps/ch, i.e. stereo 128 kbps), `BITRATE_SOURCE` (`"source"` — the same bitrate the source stream had) or an int kbps; `parse_bitrate()` normalizes `""` / `"192k"` / `192` and is the single validator for CLI + settings. `best_quality=True` prepends `BEST_AUDIO_SORT` (`acodec`, `abr`, `asr`) to yt-dlp's `format_sort`; **`acodec` has to come first** — measured, YouTube offers opus 128.9 kbps *and* m4a 129.5 kbps for the same video, so sorting by bitrate alone picks the aac stream on a 0.6 kbps nominal lead. CLI flags: `--bitrate` / `--best-quality`; 設定 has 「変換ビットレート」 / 「取得品質」 (`options/audio_bitrate`, `options/best_quality`). Two things force a **custom `FFmpegExtractAudioPP` subclass** (`_extract_audio_pp_class()`, built lazily off the runtime yt-dlp; `None` → fall back to the plain `postprocessors` dict, which is what the FakeYDL tests exercise) because both need per-video measurements and yt-dlp's PP config is fixed at construction (a playlist is one call):
  - **`"source"` bitrate** — `run()` reads `abr` (or `tbr`) out of the info dict via `source_bitrate_kbps()` and assigns `_preferredquality`; > 10 makes yt-dlp emit `-b:a <n>k`. mp3 lands on the nearest LAME step (129 → 128), aac takes the value as-is.
  - **`opus` output can skip the re-encode entirely.** YouTube's `bestaudio` *is* opus (itag 251), so with both filters off `download_tracks` selects `_COPY_FORMAT_SELECTOR[fmt]` (`bestaudio[acodec=opus]` for opus, `bestaudio[acodec^=mp4a]` for m4a) and yt-dlp remuxes with `-acodec copy` — measured, webm→ogg with the bitrate untouched. With a filter on, that preference is dropped (a re-encode is unavoidable) **and `force_encode` makes `get_audio_codec()` return a value that can't match the target**, because yt-dlp would otherwise pick `-acodec copy`, which ffmpeg refuses to combine with `-af` (`Filtering and streamcopy cannot be used together`) — or, when the download's extension already matches, skip conversion and drop the filter silently. Two related traps: **`postprocessor_args` must be a dict keyed `extractaudio`** (a flat list reaches *every* ffmpeg PP, and `-af` on `FixupM4a`'s `-c copy` remux kills the whole run — measured on an AAC-only download), and **opus's bitrate defaults to `BITRATE_SOURCE`** because libopus's own default is ~96 kbps, which silently downgrades a 129 kbps source (measured 127 → 94 kbps). A video with no opus stream just falls back to `bestaudio` and transcodes, with an INFO log line naming the codec (`is_native_codec()` / `NATIVE_CODECS`).
  - **Sample rate is pinned to the source's `asr`** (`run_ffmpeg` appends `-ar`, skipped for `codec == "copy"` and for encoders that don't accept the rate — `_ENCODER_SAMPLE_RATES`; **libopus is always excluded** since it resamples to 48 kHz itself and `-ar 44100` makes the conversion fail outright). This is a fix, not an option: **loudnorm resamples to 192 kHz internally and that rate leaks into the output** — measured on a 48 kHz opus source, m4a came out **96 kHz** and wav **192 kHz** (40 MB → 160 MB for one song) with no quality gain; mp3 hid the bug only because the format caps at 48 kHz.
- **After the bytes arrive, `download_tracks` is still busy for a while** and yt-dlp's `progress_hooks` go silent there (they only fire on `status == "downloading"`), which made the GUI look frozen at "DL中 100%". Two stages live in that gap: yt-dlp's `FFmpegExtractAudio` postprocessor (a full re-encode carrying the `-af` chain — `areverse,silenceremove,areverse` buffers the whole decoded stream **twice**, so silence-trim ON is by far the slowest part), then `_fetch_localized_title` per video (a POST to YouTube's innertube `next` API, 5 s timeout each). `on_stage(Status)` reports both — `Status.CONVERTING` from a `postprocessor_hooks` hook on `status == "started"`, `Status.FETCHING` before the entries loop. That hook deliberately **does not raise on cancel** (unlike the download hook): killing ffmpeg mid-write would leave a truncated file, so a conversion already under way finishes first — the one stage where 停止 is not immediate (the stop button's status-bar message says so). The `_fetch_localized_title` loop **is** cancellable (checked per entry), or a long playlist would sit unresponsive for 5 s × 件数.

## Running

- `uv sync` — once, to create the venv with all dependencies.
- `uv run python rename.py` — tags everything in `files/`.
- `uv run python download.py <URL> [-f mp3|wav|m4a|opus]` — single URL (default format `mp3`; `opus` + `--no-normalize` is the only re-encode-free path). `--no-ytmusic-direct` forces inference on `music.youtube.com` URLs, `--no-structured-output` drops `response_format` from the inference request (see the truncation bullet), `--best-quality` / `--bitrate <source|kbps>` control audio quality (see Pipeline specifics).
- `uv run python download.py -a urls.txt [-f ...]` — one URL per line (blank lines and `#` comments ignored).
- A playlist URL downloads all entries; a `watch?v=...&list=...` URL downloads only the single video (`noplaylist=True`). Failed playlist entries are skipped (`ignoreerrors=True`).

## GUI (`gui/`)

A PySide6 table UI that runs the full **URL → download → infer → write** flow (plus manual correction). Launch with `uv run python -m gui`. It is a thin view over `core.py`; the GUI never re-implements pipeline logic.

- **Structure**: `__main__.py` (QApplication + MainWindow), `model.py` (`TrackTableModel`, a `QAbstractTableModel`), `workers.py` (`PipelineWorker` as a `QRunnable` + `WorkerSignals`), `main_window.py` (`MainWindow`), `i18n.py` (Qt 標準文言の日本語化).
- **Japanese Qt strings**: `gui/i18n.py`'s `install_qt_translators(app)` (called right after `QApplication(...)` in `__main__.main()`) loads Qt's own **`qtbase_ja.qm`**, without which the text-box right-click menu (Undo/Cut/Copy/Paste/Select All) and dialog buttons stay English — those strings belong to Qt, not to us, so translating them means shipping the catalog, not writing menu code. Lookup order is `QLibraryInfo(TranslationsPath)` then `PySide6/Qt/translations` (the frozen-build fallback); missing catalog = silently English.
- **Threading contract (strict — spelled out in `workers.py`'s docstring)**: one pipeline at a time (`QThreadPool.globalInstance()`; MainWindow disables the run buttons while running). The worker **never touches QWidgets or the model** — it calls `core` functions, mutates `Track` dataclass fields, and emits signals. All model updates happen in MainWindow slots on the **main thread** via **queued connections** (`track_updated` → `model.refresh_track`, `tracks_ready` → `model.replace_track`, `progress` → `model.set_percent`, plus `error`/`finished`). UI reads a `Track` only after receiving its signal (relying on the queued-connection happens-before). Cancellation is a `threading.Event` (`set()` by the stop button, passed to `core.download_tracks`; infer/write check it at stage boundaries and raise `CancelledError`; see the 停止 entry under Pipeline specifics for why the exception yt-dlp sees must be a `DownloadCancelled`). **`MODE_FULL` downloads up to `max_downloads` URL rows at once** — `_download_all` runs `_download_one` on a `ThreadPoolExecutor` (default `core.MAX_DOWNLOADS` = 2, settable in 設定). This exists because yt-dlp serializes receive → ffmpeg convert → next *within* one call and offers no way to background its postprocessors (its only concurrency flag, `--concurrent-fragments`, splits a single video), so without crossing rows the link sits idle through every conversion; a playlist entered as one row is still serial inside yt-dlp (expand it with [情報取得] first). Table order survives because `replace_track` finds the placeholder by identity and swaps it in place. `_download_one` swallows its own exceptions and returns `True`/`False`/`None` (cancelled) so the caller can count the stage summary without a lock; only `publish()` (append to `ready` + hand off to the infer stage) is serialized, and `core.ensure_ytdlp()` takes a lock so a first-use race can't have two threads editing `sys.path`. **`MODE_FULL` also runs DL and inference concurrently** — `_InferStage` (workers.py) owns one extra thread (`ThreadPoolExecutor(max_workers=1)`, so the LLM never sees two requests at once) and `_download_all(on_ready=stage.feed)` hands it each finished row; once `batch_size` inferable rows have piled up, that chunk goes to `core.infer_titles` (+ `core.write_tags` when auto-write is on) **while the remaining URLs keep downloading**. The leftover < `batch_size` rows are flushed in `close()`, so a run shorter than one batch behaves exactly as the old serial path did. Ownership of a `Track` moves DL-thread → infer-thread at `feed()` and never comes back, so no row is touched by both; `tracks_ready` is emitted *before* `feed()`, and the posted-event queue is FIFO, so the model always sees the row before its first `track_updated`. `_write_tracks` (no emit) is split out of `_run_write` so per-batch writes accumulate into **one** `write_summary` at the end. An inference failure records the first exception, stops further batch submission (so a dead LLM doesn't fail once per row), lets the downloads finish, and is re-raised on the worker thread afterwards → the usual `error` signal.
- **[再生リストを無視] checkbox (toolbar)**: the inverse of the 設定 dialog's `expand_playlist` (`options/expand_playlist`), surfaced next to 自動書き込み because it's a per-run decision. Checked (the default, matching the existing behaviour) = `expand_playlist=False` = `noplaylist=True` = a `watch?v=...&list=...` URL is treated as the single video; unchecking expands the whole list. The two controls stay in sync in both directions (`_on_noplaylist_toggled` writes the same QSettings key, `apply_settings` / `_restore_settings` push the value back into the checkbox).
- **Row lifecycle**: adding a URL inserts a placeholder `Track` (`stem=url`, `url=url`, `status=QUEUED`) immediately; on download completion `tracks_ready` replaces that placeholder with the real `Track` row(s) (a playlist expands to several rows). Inference batches `QUEUED`/`PENDING`, non-`manual` rows into `core.infer_titles` calls of `batch_size` rows (never per-row) — in `MODE_FULL` fed incrementally as downloads finish (see the threading contract above), in `MODE_INFER` as one call over the selection. Auto-write ON → `core.write_tags`; OFF → stops at `PENDING`. The [情報取得] button runs `MODE_FETCH` (`core.fetch_metadata`, rows show `Status.FETCHING` with the busy-blue tint): it expands **only untouched placeholder rows (`stem == url`, no `filepath`)** into metadata rows (title/channel, still `filepath=None`/QUEUED — a later 実行 downloads them normally) without downloading, for inspecting large playlists first; already-expanded and local rows are skipped, so re-running never overwrites manual edits. When a fetched row is later downloaded, `_download_all` **carries over manual edits (title → `manual`/`valid`/`PENDING`, and artist)** onto the real `Track` before `tracks_ready` — single-track results only (a playlist expansion can't be mapped back to one row's edits). URL lists come in via the [リスト読込] button, a **`.txt` drop** onto the table, or **Ctrl+Enter in the URL box** (an eventFilter on `_url_edit` — not a QShortcut — so tests can drive it without focus). Local-file adds ([ファイル追加] / [保存先から取り込み] / audio-file drop — all through `MainWindow.add_files`) **skip files already in the table** (resolved-`filepath` comparison, within the batch too), so pressing 取り込み repeatedly never duplicates rows; [保存先から取り込み] scans `self._out_dir or core.FILES_DIR` (follows the settings dialog's save-dir, not a hardcoded FILES_DIR). Every local add goes through `core.track_from_file`, so the row arrives with the file's existing 曲名/作者/アルバム already in place and editable; `add_files` counts how many rows had readable tags in `self._last_tagged` purely for the status-bar message. An empty table paints a hint text (`_DropTableView.paintEvent`) advertising the URL→追加→実行 flow and drag&drop.
- **Search (行の絞り込み)**: the [検索] button and **Ctrl+F** (a `QAction` with `QKeySequence.StandardKey.Find` on the window, so it fires wherever focus is) open a search bar between the banner and the table; typing hides every row that doesn't match, and the label shows `表示 / 全体` (or 「一致なし」). Matching is `TrackTableModel.matches(row, query)` — a case-insensitive substring over `row_text(row)`, which is just **every column's display string joined**, so 状態 and the error text shown in 推定タイトル are searchable too (no kana/width normalization: typed text matches literally). **No `QSortFilterProxyModel`** — for the same reason `sort()` reorders the list in place: the worker finds rows by identity and the percent dict is keyed by row number, so a proxy's row mapping doesn't fit. Hiding rows in the view leaves every row number untouched, which is why searching **while a pipeline is running** is safe (and deliberately left enabled by `_set_running`). `_apply_filter()` is re-run on `rowsInserted` / `rowsRemoved` / `layoutChanged`, and on `dataChanged` **only for the changed rows** (that signal fires per progress tick during DL); it early-returns entirely when nothing is or was hidden. Because a hidden row keeps its selection, **`_selected_rows()` drops hidden rows** — otherwise 書き込み/行削除 would hit rows the user can't see — and `_on_fill_artists`'s 「未選択なら全行」 falls back to `_visible_rows()`. Esc / ✕ clear the filter *and* close the bar (closing while rows are hidden would look like the rows were deleted); Enter moves focus to the table.
- **Model specifics**: columns `#` / 元タイトル(stem) / チャンネル / 推定タイトル / アーティスト / アルバム / 状態 / 形式 — the three metadata fields sit together in tag order (曲名 → 作者 → アルバム名). Title, artist and album columns are editable (`EDITABLE_COLUMNS`); `setData` on the title column (delegating to `set_title`) sets `guessed_title`, `manual=True`, `status=PENDING`, and manual rows render with a `✎ ` prefix. The artist column (`set_artist`) is **never inferred by the LLM** — typed manually, bulk-filled from `Track.channel` via the [チャンネル名→アーティスト] button (undoable macro), or filled from YouTube Music (see Pipeline specifics); editing it doesn't touch `manual`, but flips `DONE` rows back to `PENDING` so they get rewritten (`core.write_title` writes `TPE1`/`©ART` only when artist is non-empty). The アルバム column (`set_album`, `EditAlbumCommand`) behaves exactly like アーティスト — never inferred, no `manual`, `DONE` → `PENDING` on edit — and is filled from the file's existing tag on import. After any write, the worker emits `write_summary(done, skipped, errors)` shown in the status bar; fetch/download stages likewise emit `stage_summary(stage, done, errors)` (only when ≥1 row was attempted) so failures don't drown in a final「完了」. The undo state tuple (`title_state`) carries `skip_infer` too. `sort(column, order)` reorders `self._tracks` in place (no `QSortFilterProxyModel`; `#` column is a no-op, percent dict cleared). Download percent lives in a `row→percent` dict inside the model (no display field added to `Track`). Background colors: DONE=green / ERROR=red / PENDING+`valid is False`=yellow / FETCHING·DOWNLOADING·CONVERTING·INFERRING=blue; tinted rows also force a dark `ForegroundRole` (OS dark themes default to white text, unreadable on pastels). ## Packaging (PyInstaller)

The GUI ships as a **onedir** build: Windows `dist/FileRenameGUI/` (exe) and macOS `dist/FileRenameGUI.app` (Apple Silicon). **Neither ffmpeg nor yt-dlp is bundled** — ffmpeg is installed by the user (winget / brew; the app warns at startup and before 実行, see GUI section), and yt-dlp is fetched at runtime by `ytdlp_runtime` (see below).

- **Build**: `./build.ps1` (Windows) / `./build.sh` (mac) → `uv sync` + `uv run pyinstaller file_rename_gui.spec --noconfirm`, then copies `.env.example` + `README_dist.md` into `dist/`. PyInstaller can't cross-compile — the mac build runs on a mac with the same sibling layout (`../mv2title` editable dep). `pyinstaller` is in the dev dependency group.
- **`file_rename_gui.spec`** is one cross-platform file: entry point `run_gui.py` (PyInstaller can't take `-m gui`), `hiddenimports=["PySide6.QtMultimedia"]` (lazy import in `gui/player.py`; yt-dlp ships its own hook, which still runs — see the strip below), `datas` carrying **`qtbase_ja.qm` → `PySide6/Qt/translations`** (the PySide6 hook doesn't bring translations along, and without it the frozen app's text-box context menus revert to English), `console=False`, and a `BUNDLE(...)` block under `sys.platform == "darwin"` (no `codesign_identity` → PyInstaller ad-hoc-signs on arm64; personal distribution, no notarization — recipients use right-click→開く or `xattr -cr`). `build.sh` zips the .app with `ditto -c -k --keepParent` to preserve attributes.
- **Frozen-path rules**: never use `__file__`-relative paths for user-facing files — go through `core.app_dir()` / `core.find_env_file()` (see the wiring section). The distributed `.env` lives **next to the exe / .app**, not inside `_internal`.
- **yt-dlp is NOT bundled** — it goes stale within months (YouTube's signature / n-challenge changes make every download 403), and baking it into the PYZ meant rebuilding and redistributing the exe each time. `ytdlp_runtime.py` instead downloads the PyPI **wheel** (`py3-none-any`, zero mandatory deps — all extras) with `urllib` + `zipfile` (no pip) and extracts it to a **version-named** directory under the per-user data dir (`%LOCALAPPDATA%/FileRenameGUI/runtime/<version>/`, mac `~/Library/Application Support/...`); a pre-seeded `core.app_dir()/runtime` wins if present (offline distribution). Version dirs are never overwritten in place — install extracts to `.staging-*` and `rename`s, so a failed fetch can't break the working copy, and `prune()` keeps 2 generations for rollback. The per-user dir (not next to the exe) is deliberate: macOS **App Translocation** runs a quarantined `.app` from a read-only random path, so "next to the app" isn't reliably writable. `core.YoutubeDL` starts as `None` and `core.ensure_ytdlp()` fills it on first use — it **returns early when already set**, which is what keeps `monkeypatch.setattr(core, "YoutubeDL", FakeYDL)` in the tests from touching `sys.path` or the network.
- **EJS (`yt-dlp-ejs`) rides along with yt-dlp** — the JS that solves YouTube's signature / n challenges does not live in yt-dlp itself. Without it yt-dlp warns `Signature solving failed` / `n challenge solving failed` and wants to fetch the scripts per-run from GitHub or npm (`--remote-components ejs:github` / `ejs:npm`), which is disabled by default. `ytdlp_runtime.install_ejs(target)` instead extracts the `yt-dlp-ejs` wheel **into the same version directory as yt-dlp**, which keeps one `sys.path` entry, pins the pair together, and lets `prune()` drop both generations as a unit. The version is **not** "latest": `required_ejs_version()` reads the exact pin out of the downloaded yt-dlp's own `yt_dlp-*.dist-info/METADATA` (`Requires-Dist: yt-dlp-ejs==X`), because yt-dlp verifies the script against a vendored hash list and rejects a mismatched major.minor — a wrong version is as good as no EJS. The package route is preferred over `remote_components` deliberately: it is the highest-priority script source (`ScriptSource.PYPACKAGE`), it is hash-checked by yt-dlp, and it means downloads never reach out to github.com/npm at run time. Swap of an existing EJS goes through a staging dir and rolls the old tree back on failure; a failed EJS fetch never fails the yt-dlp update itself (downloads still work, just degraded).
- The spec's `_strip_ytdlp` covers **both** `yt_dlp` and `yt_dlp_ejs`, and matches **module names (`pkg.`) and data paths (`pkg/`, `pkg\\`)** — `a.datas` carries `yt_dlp_ejs/yt/solver/*.min.js` under path-style names, so a dot-only filter leaves the JS behind (and a data-only `yt_dlp_ejs/` directory in `_MEIPASS` can still be imported as a namespace package, shadowing nothing today but a trap). Bundling EJS would be actively harmful: the PYZ resolves before `sys.path`, so a frozen copy would hide the runtime-installed matching version.
- **`--selftest` (diagnostic)** — `run_gui.py` dispatches `--selftest` to `selftest.py` before any Qt import, so a frozen build can be checked from a terminal (`console=False` means the GUI build otherwise prints nowhere): it lists frozen-ness / `app_dir()` / `.env` / `FILES_DIR`, finds ffmpeg + deno, loads the runtime yt-dlp, and does an HTTPS GET to PyPI (the frozen TLS path — the classic thing that only breaks after packaging). `--update` runs the same fetch/update as the 設定 dialog (terminal fallback when the GUI can't be driven), `--download <URL>` pulls one track into a temp dir and deletes it (proves yt-dlp → deno → ffmpeg subprocesses work from inside the bundle). Labels are padded by **display width** (`unicodedata.east_asian_width`), not character count, or the Japanese labels misalign. On macOS run `FileRenameGUI.app/Contents/MacOS/FileRenameGUI --selftest`; on Windows the GUI-subsystem exe has no console, so redirect: `FileRenameGUI.exe --selftest > log.txt`.
- **macOS build verified** (2026-08-28, macOS 26.6 / Apple Silicon): fetch → load → metadata → download → mp3 all pass from the frozen `.app` (`--selftest --update --download`, incl. a fresh install with `HOME` pointed at an empty dir). PyInstaller's mac bootloader sets **no `DYLD_LIBRARY_PATH`** (checked with `ps eww` on the running app), so the ffmpeg/deno subprocesses aren't at risk of loading the bundle's dylibs.
- **The spec must NOT `excludes=["yt_dlp"]`** — that stops the analysis from walking yt-dlp's imports, so stdlib modules only it needs (`optparse` first, then more) never get collected and the external yt-dlp dies with `ModuleNotFoundError`. Let the analysis run, then drop the collected `yt_dlp.*` entries from `a.pure` / `a.datas` (`_strip_ytdlp` in the spec). Measured: PYZ 14.7MB → 9.3MB, exe 15.0MB → 9.7MB, 1043 modules removed. yt-dlp therefore stays a **runtime dependency in `pyproject.toml`** — the build needs it installed for the analysis, and it's the dev fallback when no runtime dir exists.
- **A JS runtime (deno) is effectively required** for YouTube: without one yt-dlp still downloads but the n-challenge goes unsolved and throughput collapses (measured 1.7 MiB/s vs 12–32 MiB/s), plus yt-dlp warns the path is deprecated. Checked at startup and before 実行 exactly like ffmpeg (`_check_external_tools()` / `_confirm_deno()` / `_deno_install_hint()`), except the pre-run dialog defaults to **Yes** — unlike ffmpeg, a missing deno degrades speed rather than breaking the output. Only `deno` is probed: it is the only runtime yt-dlp enables by default (a `node` on PATH is not used without `--js-runtimes`).
- `build/` and `dist/` are gitignored; the `.spec` is committed.

## Dependencies / gotchas

- **ffmpeg on PATH** is still required for `download.py`'s mp3/wav conversion (not pip-installable).
- **`yt-dlp-ejs`** is declared in `pyproject.toml` next to `yt-dlp` for the same two reasons: the dev venv fallback (no extracted runtime dir → plain `import`) and PyInstaller's analysis. The frozen build strips both.
- Requires a running OpenAI-compatible LLM endpoint configured via `.env` (dev: `../mv2title/.env`; see that package's CLAUDE.md) or the GUI 設定 dialog overrides.
- Indentation here is **4 spaces** (unlike the mv2title package, which uses tabs); comments/docstrings are Japanese.
